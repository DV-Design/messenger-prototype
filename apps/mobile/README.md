# LastCall · Android и iOS

Версия 0.6.0 / Android versionCode 9. На собственном Android-эмуляторе проверены холодный FCM-запуск и передача текста/файла 35 байт без нажатия; физические телефоны и российские сети требуют отдельной проверки. Package ID `dev.messenger.prototype` и ключ подписи сохраняются для обновления без удаления данных. Основной сервер: `https://lienad.ru/messenger`.

Светлый интерфейс со стандартными системными шрифтами: вкладки «Чаты», «Контакты», «Настройки», личные диалоги и группы до 8 участников. Телефон, SMS и доступ к телефонной книге больше не нужны.

## 0.6.0 / Android code9

Текущая версия — 0.6.0/code9. Добавлены зашифрованные
preview текста/имени файла, переход из уведомления в нужный личный/групповой чат,
системные Android-звонки, голосовые сообщения и видеокружки.
[Точная нативная приёмка и ограничения](../../docs/reports/debugging/2026-10/native-060.md).
Не считать наличие source/unit-тестов доказательством работы на API 36 или телефоне.

Обновлённый получатель отдельно заявляет `messagePreview:true` только при готовой
фоновой задаче и нативном отображении. База токенов мигрирует с default 0; старые
0.5.1 получают прежнее общее уведомление. Отправитель шифрует текстовый preview
pair-derived HKDF/XChaCha20-Poly1305 с привязкой sender/recipient/intent/deadline.
Текст ограничен 800 байтами UTF-8, целые Unicode code points; JSON-escaping может
сократить его раньше. Конверт ограничен 3000 байтами, весь FCM data payload — 4 КБ.
Для файлов разрешён только зашифрованный preview имени, без файловых байтов.
SDP и секретные ключи туда не входят. FCM временно хранит
зашифрованный конверт до 60 с; это не серверная DB-очередь полной переписки.

Расшифровка разрешена только для pinned-контакта и существующего личного/группового
чата с проверенным участием. Имя берётся из локального профиля контакта, а не из
доверенного текста push. Неверные ключ/срок/intent/членство отклоняются. Preview
не вызывает content ACK и не создаёт чат/историю. Реальный P2P-приём после записи
может обновить то же уведомление без дубликата. Для текста на secure lockscreen
нужен `VISIBILITY_PUBLIC` на самом Android notification: настройки Expo channel
одной недостаточно. Нативный адаптер проверен на собственном эмуляторе; системные настройки
пользователя могут скрыть даже PUBLIC-уведомления.

CallKeep 4.6.1 подключает managed Android Telecom/ConnectionService. Пользователь
в foreground нажимает «Настроить системные звонки», выдаёт `READ_PHONE_NUMBERS` и
`CALL_PHONE`, затем включает аккаунт LastCall. `READ_CONTACTS`/`READ_CALL_LOG` не
запрашиваются; регистрация по username не меняется. Ringing требует действующий
callId из аутентифицированного live-сеанса, а не wake payload. Ring-service имеет
тип `phoneCall` (4) без microphone. После явного ответа и заранее выданного
`RECORD_AUDIO` audio-service использует `phoneCall|microphone` (132), затем WebRTC
открывает аудио. Reject/end/cancel/expiry должны убрать системный вызов, остановить
service и освободить runtime; повторное действие не отвечает на другой вызов.

Холодная задача по-прежнему ограничивает обычную синхронизацию окном 9 с. Живой
звонок удерживает владельца runtime и нативную lease ReactHost до завершения.
Собственный app-loader wrapper, установленный config plugin через manifest-provider,
откладывает SDK58-инвалидацию хоста только пока lease удерживается; `node_modules`
не патчатся. Это не разрешение непрерывно выполнять обычную фоновую синхронизацию.
See the native acceptance report above for secure-lockscreen system answer,
actual notification routes, bounded task cleanup and media evidence. Physical
Android/Russian carriers and iOS/APNs/CallKit remain separate.

[Android service types](https://developer.android.com/develop/background-work/services/fgs/service-types).

## Уведомление открывает чат — 0.6.0

Нажатие на уведомление текста или файла должно открыть существующий чат
отправителя; для группового сообщения открывается соответствующая группа.
Холодный запуск сначала восстанавливает прежний профиль и зашифрованное состояние,
потом проверяет sender/recipient, ключ контакта, членство и область server/identity.
Внешний URL из payload не используется; отсутствующий или подменённый чат не
создаётся по уведомлению. Само нажатие не помечает ожидающее содержимое доставленным.
Старые общие уведомления могут только открыть приложение, без точного маршрута.

## Голосовые сообщения и видеокружки — 0.6.0

В пустой строке ввода кнопка микрофона открывает «Голосовое сообщение»;
скрепка → «Голосовое» открывает тот же экран. Нажмите «Начать запись», затем
«Остановить», прослушайте preview кнопкой воспроизведения и выберите «Отправить»
или «Удалить и закрыть». До готового preview доступна «Отмена».

Для видео: скрепка → «Видеокружок» → «Включить камеру» → «Начать запись».
Используется фронтальная камера. После «Остановить» можно посмотреть запись,
отправить либо удалить её. Голос ограничен 120 с, видео — 30 с; native recorder
и таймер ограничивают длительность. Перед отправкой повторно проверяются байты:
не более 5 МиБ. Во время зашифрованного сохранения после «Отправить» отмена
заблокирована; уже принятую запись в очереди отмена/сворачивание не отзывает.

Голос: AAC mono 64 кбит/с, M4A / `audio/mp4`. Видео: целевые 480p на Android,
640×480 на iOS, 600 кбит/с; Android сохраняет MP4 / `video/mp4`, Expo Camera на iOS —
MOV / `video/quicktime`. Устройства могут выбрать другой поддерживаемый размер;
лимит байтов проверяется независимо. Inline-тип определяется только сочетанием
зарезервированного имени `lastcall-voice-<32 hex>.m4a` или
`lastcall-circle-<32 hex>.mp4|mov` и соответствующего MIME; обычные вложения
продолжают открываться через меню сохранения.

Голос проигрывается прямо в чате с паузой и прогрессом; видеокружок — с паузой
в круглом окне. **Круг — обрезка интерфейса. Сохранён полный прямоугольный кадр**,
включая скрытую область: при сохранении или просмотре вне LastCall она может быть
видна. Запись не вырезает эти пиксели и не делает их приватными.

`expo-audio`, `expo-camera` и `expo-video` SDK58 используются для записи/просмотра.
Заметки не записываются в фоне и не запускаются от push. Уход с экрана, фон,
отмена до отправки и ошибка освобождают recorder/camera и удаляют временную
запись; поздний результат разрешения или чтения не должен отправить её. Во время
звонка запись недоступна, а входящий звонок отменяет незавершённую запись.
Отказ в доступе не должен создавать пустое вложение.

Расшифрованная копия для playback создаётся лениво только при нажатии и удаляется
при уходе с экрана/в фон, смене проигрываемой записи либо через 180 с. Одновременно
звуком владеет один player. После убитого процесса оставшиеся копии из выделенных
media-cache путей очищаются при следующем использовании media; это очистка cache,
а не гарантия физического стирания памяти носителя. Share-копия удаляется после
закрытия системного меню. Зашифрованная история этими действиями не удаляется.

Готовая запись идёт через существующий `sendFile` и encrypted attachment adapter:
сначала зашифрованное сохранение, затем P2P/TURN, ACK только после записи получателя.
Семь дней считаются с исходной отправки; повтор передаёт файл целиком. Общее
хранилище остаётся 16 файлов / 40 МиБ, включая подтверждённые записи. До отправки
черновик локальный; на сервер не добавляется медиахранилище.
Старый клиент может показать такую запись обычным вложением; для inline-управления
обновляются оба телефона. Нативная проверка реальных камеры, звука, отмены, лимитов
и освобождения ресурсов остаётся обязательной на финальной 0.6.0;
source/unit-тесты её не заменяют.

Первичные источники SDK58: [Audio](https://docs.expo.dev/versions/v58.0.0/sdk/audio/),
[Camera](https://docs.expo.dev/versions/v58.0.0/sdk/camera/),
[Video](https://docs.expo.dev/versions/v58.0.0/sdk/video/).

## Регистрация и ключ устройства

Один ключ установки владеет одним неизменяемым логином на выбранном сервере. Логин уникальный: 3–24 латинские буквы/цифры/underscore, без учёта регистра. Отображаемые имена могут повторяться. Регистрация считается завершённой только после подтверждения сервера; никакой Firebase Authentication для неё не требуется.

Если локальный профиль отсутствует, `resolveDeviceProfile` подписывает отдельный серверный challenge существующим ключом. Только подтверждённый ответ `null` разрешает форму регистрации; сеть/timeout не трактуются как отсутствие привязки. Уже зарегистрированный ключ восстанавливает канонический серверный профиль. Потеря ответа регистрации или ошибка локального сохранения не дают выбрать второй логин. Повторное нажатие блокируется синхронным process-level busy guard.

Канонические имя/логин из `ready.self` сохраняются только при изменении. Записи SecureStore сериализованы и дедуплицируются; ошибка сохранения не отменяет привязку на сервере. Seed Ed25519 остаётся в существующем SecureStore record (`WHEN_UNLOCKED_THIS_DEVICE_ONLY` на iOS), не попадает в файловую систему и никогда не регенерируется для исправления ошибки регистрации. Старые ключи телефонного сценария не читаются и не удаляются. Потерянный ключ нельзя восстановить по публичному логину.

При наличии локального профиля открывается кешированная история даже без сети. `runtime.ts` владеет одним `MessengerClient` на процесс; навигация и обычный background не разрывают контакты/звонок. Смена сервера сначала проверяет привязку того же ключа, затем подключается к выбранному серверу; история хранится отдельно для каждого server/identity.

## Каталог пользователей

Вкладка «Контакты» показывает каталог сервера отдельно от сохранённых чатов. `listUsers(cursor?)` загружает страницы до 100 пользователей; кнопка «Загрузить ещё» использует серверный keyset cursor. Сами строки каталога не создают контакты, чаты или P2P-сессии. Только выбор человека открывает чат.

Поиск по полному серверному каталогу принимает имя или @логин, включая русские имена: NFKC, trim, удаление ведущего @, lower-case. Debounce 350 мс; поколения запросов исключают перезапись новым запросом старым ответом и присоединение старой страницы к новому поиску. Новый server/identity получает отдельный controller. При отсутствии сети каталог явно помечается как необновляемый; сохранённые чаты остаются на вкладке «Чаты».

Обновление идёт при фокусе вкладки, reconnect, foreground resume и каждые 30 секунд, пока вкладка видима и приложение активно. На background/потере фокуса таймеры и актуальность запросов отменяются. Кнопка обновления и pull-to-refresh доступны отдельно. Каталог сохраняется только в памяти.

## История и передача

Core шифрует контакты, группы, недавний текст и локальную очередь ожидающих сообщений. FileSystem-адаптер пишет только sealed ciphertext последовательными записями через временный файл и `move(overwrite: true)`, с пределом, согласованным с core. Повреждённые данные не сбрасываются молча.

Сообщения и звонки идут по защищённому WebRTC соединению; при наличии настроенного сервера TURN возможен relay. Текстовые статусы: часы — ожидает, одна отметка — отправлено, две — ACK получателя, не прочтение. Файлы до 5 МиБ сохраняются зашифрованно до отправки и ожидают подтверждения до семи дней от исходной отправки. Очередь и байты восстанавливаются после перезапуска; попытка повторяет файл целиком. Лимит — 16 сохранённых файлов / 40 МиБ, включая подтверждённую историю. Переполнение возвращает ошибку без удаления ожидающих данных. Preview/share используют временный cache с очисткой.

## Готовность к передаче данных

В 0.5.1 также исправлено начало передачи по native WebRTC 155:
канал мог уже открыться до подключения JavaScript-обработчиков, и первые текст
или части файла терялись. Теперь между обновлёнными клиентами перед отправкой
проверяется готовность принимающей стороны. Этот этап не заменяет ACK после
записи сообщения/файла. Для защиты нужно обновить оба приложения до 0.5.1;
финальный APK прошёл проверку холодного фонового запуска и небольшого файла
на собственном эмуляторе. Это не проверка всех устройств и файлов до 5 МиБ.

Технически возможность согласуется экспериментальным атрибутом
`a=x-lastcall-data-ready:1` внутри аутентифицированного signaling; перед native
SDP он удаляется. После установки обработчиков используется случайный challenge
канала и `ready`/`ready-ack`: повтор через 250 мс, предел 5 с и 64 кадра за 5 с.
Без согласования у обеих сторон новые кадры не отправляются, действует прежнее
поведение. При восстановлении готовность также проверяется до отправки данных.

## Разрешения и push

Остались только камера, микрофон, фото/видео и уведомления. При первом запуске после локальной загрузки ключа, до завершения сетевой проверки регистрации, открывается экран доступов. Системные запросы автоматически идут в порядке микрофон → камера → фото → уведомления; отказ или ошибка одного не мешает остальным. ОС сама решает, нужен ли запрос для уже доступной категории. Повторное событие foreground не запускает новую последовательность; перед первым запросом сохраняется attempted marker, после завершения — done. Завершённый marker прежней версии сохраняет силу. В настройках остаются индивидуальные и повторные ручные запросы. Камера/микрофон не включаются для проверки доступа. `expo-contacts`, телефонные экраны и READ/WRITE_CONTACTS удалены из активного продукта. Старые пользовательские данные не очищаются.

Android FCM независим от регистрации. Firebase-проект и клиентская конфигурация
подключены, серверная отправка включена. При сборке нужен
`MESSENGER_GOOGLE_SERVICES_FILE` с отдельной клиентской конфигурацией; тот же env
передаётся native prebuild и JS/native build. Без него `extra.nativeFcmConfigured=false`
и token API не вызывается. Firebase Admin JSON никогда не входит в приложение.

Канал `lastcall-messages` создаётся до permission/token. Native токен получается
через SDK58 `getDevicePushTokenAsync`, регистрируется после authenticated directory
online; listener обрабатывает rotation. На 0.5.0/code6 подтверждены настоящее
общее уведомление после Home и обычного завершения процесса, открытие по нажатию
и последующий P2P-текст с durable ACK. Force-stop в этой проверке не использовался.
Регистрация токена и принятие push провайдером сами по себе не подтверждают приём.

В 0.5.1 подключена SDK58 TaskManager-задача, определённая до Router. Только успешная
регистрация задачи позволяет передать `backgroundSync:true` при регистрации токена.
Для такого токена сервер выбирает data-only FCM с общим видимым уведомлением;
legacy-токены сохраняют notification+data и открытие по нажатию. В опубликованной 0.5.1 push остаётся общим. В 0.6.0 он может нести
ограниченный зашифрованный preview; открытый текст, имена/байты файлов, SDP и
секретные ключи серверу/FCM не передаются. Каталог
хранит профиль, имя и публичный ключ; signaling пересылает непрозрачные
зашифрованные SDP/candidate envelopes. Секретный seed остаётся на устройстве.

Фоновая попытка использует тот же Android ReactHost и существующий runtime,
профиль, ключ и encrypted storage. Она не создаёт нового пользователя, не открывает
разрешения/микрофон и не отвечает на звонок. Транспортное окно ограничено примерно
9 секундами; запись в хранилище должна завершиться в пределах короткого бюджета ОС.
Переход в foreground передаёт владение текущему runtime, не создавая параллельные
пишущие менеджеры. На финальном APK подтверждено отсутствие завершённого процесса;
FCM затем запустил синхронизацию без нажатия и без
вывода экрана приложения. Текст и файл 35 байт получили durable ACK через 5728 мс
в одном запуске по прямому маршруту. Отдельно проверен переход из холодной фоновой
задачи в foreground: оба ACK через 6786 мс, с автоматическим восстановлением после
одной временной ошибки сеанса. При отключённой сети после force-stop и ручного
открытия сохранённые текст и вложение остались видимы офлайн; профиль сохранился.
Force-stop использовался здесь для проверки сохранения, а не получения push.
Это результаты опубликованной 0.5.1. Физические телефоны и российские операторы
остаются отдельным этапом; промежуточные lockscreen-результаты новой ветки описаны выше.

Серверного mailbox нет: отправитель или участник группы с проверенной копией должен
быть доступен. Android force-stop блокирует push до ручного открытия. Выключенный
телефон, отсутствие сети, ограничения батареи и ОС могут задержать пробуждение.
Google Play Services, разрешение уведомлений и проверки на физических телефонах
остаются необходимыми. iOS/APNs/CallKit и групповые звонки не реализованы.
Голосовые, видеокружки и Android Telecom добавлены в 0.6.0. Точная эмуляторная
приёмка приведена в отчёте выше; физические телефоны остаются отдельным этапом.

## Запуск и проверки

Из корня после установки workspace-зависимостей:

```sh
npm run typecheck -w @messenger/mobile
npm run lint -w @messenger/mobile
npm run test -w @messenger/mobile
npm run build -w @messenger/mobile
```

`build` экспортирует Android/iOS JS/resources; APK/IPA и native execution не проверяет. Собственный ранний entry регистрирует фоновую задачу перед загрузкой Expo Router из `src/app`. Expo Go не включает WebRTC; нужна native/dev-сборка. Android требует JDK/Android SDK, локальная iOS-сборка — полный Xcode; `eas.json` содержит профили облачной сборки.

```sh
npm run native:prebuild -w @messenger/mobile
npm run android -w @messenger/mobile
npm run start -w @messenger/mobile
```

Focused tests проверяют доступы, регистрацию/каталог, маскирование диагностики, состояния семидневной очереди и сериализацию/актуальность событий сети. Отдельные core-тесты проверяют шифрование вложений, durable ACK, срок, подписи и передачу; Chrome — реальные байты и ICE/аудио. Нативное обновление и FCM/headless-приёмка проверяются отдельно; SMS не является частью продукта.

Адрес можно изменить в настройках. Префикс gateway сохраняется. Для локального HTTP задайте `MESSENGER_ALLOW_LOCAL_HTTP=1` при prebuild и `EXPO_PUBLIC_ALLOW_LOCAL_HTTP=1` при JS/native build; валидатор допускает только LAN/loopback/`.local`. Публичные endpoint используют HTTPS. Генерируемые android/ios не редактируются вручную.

Прямое соединение раскрывает IP собеседнику. Double Ratchet/key transparency/независимый аудит и невидимость для DPI не заявляются. Удаление приложения может лишить ключа и локальной истории.

## Android release: WebRTC 155 и R8

Expo 58 генерирует `android.enableMinifyInReleaseBuilds=true`. Минификация остаётся включённой. `plugins/withWebRtc155Release.cjs` добавляет только правило `-dontwarn org.webrtc.Dav1dDecoder$Natives` и строгий Gradle constraint на `org.jitsi:webrtc:155.0.1`, заменяющий плавающий upstream-диапазон `155.+`.

Причина: в проверенном AAR 155.0.1 остался `org.webrtc.Dav1dDecoderJni`, хотя Java-обёртка `Dav1dDecoder` и её `Natives` не упакованы. `jar`/`javap` и проверка ссылок всех классов показали, что имя Dav1d встречается только в этом неиспользуемом bridge и native-объявлении `org.jni_zero.GEN_JNI`. Действующие `SoftwareVideoDecoderFactory` и его anonymous decoder вызывают собственный `SoftwareVideoDecoderFactoryJni` и C++ decoder factory. Они не создают отсутствующую Java-обёртку Dav1d. Правило не меняет factory, кодеки и native-библиотеки; общего подавления ошибок `org.webrtc.**` нет.

Проверенный AAR: SHA-256 `b686b7674fd7285ddda369e155ca9663b9787f2b2f470b76691980782e13cd26`. При обновлении WebRTC нужно пересмотреть plugin и повторно проверить содержимое AAR. Это исправление упаковки для R8; работоспособность AV1 на конкретном устройстве этим анализом не подтверждается.

Первичные источники: [upstream Dav1d Java wrapper](https://webrtc.googlesource.com/src/+/main/sdk/android/api/org/webrtc/Dav1dDecoder.java), [SoftwareVideoDecoderFactory](https://webrtc.googlesource.com/src/+/main/sdk/android/api/org/webrtc/SoftwareVideoDecoderFactory.java), [его C++ JNI implementation](https://webrtc.googlesource.com/src/+/main/sdk/android/src/jni/software_video_decoder_factory.cc), [upstream consumer keep rules](https://github.com/react-native-webrtc/react-native-webrtc/blob/master/android/consumer-rules.pro).
