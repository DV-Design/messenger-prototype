# Архитектура первого прототипа

Дата решения: 2026-10-27. Название каталога — техническое, название продукта не выбрано.

## Объём

Прототип проверяет связь двух устройств: текст, ограниченные по размеру файлы,
аудио/видео 1:1, прямой и принудительно ретранслируемый маршрут. Мобильное приложение
работает в активном состоянии. Боты, каналы и резервные копии исключены.
Группы, офлайн-доставка, длительные передачи с восстановлением после перезапуска
и фоновые входящие вызовы остаются следующими этапами.

## Выбранный подход

Expo development build + React Native WebRTC для общей мобильной реализации,
TypeScript core для одинакового поведения в приложении и браузерном испытательном
клиенте. Это выбор для проверки транспорта; он не предрешает язык будущего ядра.
Собственный Rust core имеет смысл после измерений, если потребуются дополнительные
транспорты или преимущества разделяемого нативного состояния.

Служебный сервер передаёт зашифрованные параметры WebRTC и уведомления о присутствии
двух устройств. Содержимое чата и файлов проходит по WebRTC DataChannel. Медиа идёт
по WebRTC SRTP. ICE выбирает маршрут; TURN нужен при невозможности прямого пути.
Принудительный режим relay должен завершаться понятной ошибкой без настроенного
TURN, а не незаметно раскрывать прямой адрес.

Публичные STUN/TURN-сервисы не подключаются по умолчанию. У оператора приложения
должен быть осознанный выбор своей инфраструктуры. Сервер по умолчанию слушает
loopback; выход в локальную сеть требует явной конфигурации.

## Приглашение и доверие

Два участника получают один случайный секрет 256 бит через другой доверенный канал.
Из него выводится непрозрачный идентификатор комнаты и ключи шифрования служебных
пакетов. Секрет не передаётся серверу и не должен находиться в query-параметрах,
серверных логах или коммитах. Аутентифицированное шифрование связывает SDP и его
DTLS fingerprint с приглашением. Подмена содержимого сервером должна обнаруживаться.

Это экспериментальная схема с предварительно разделённым секретом. Она не даёт
постоянной идентификации контактов, key transparency, Double/Triple Ratchet,
отзыва устройств или производственных гарантий безопасности. До использования
для чувствительной переписки необходим отдельный дизайн и аудит.

## Метаданные

Сервер видит IP подключившихся устройств, время, принадлежность одной непрозрачной
комнате и размеры служебных пакетов. Прямое P2P раскрывает IP собеседнику. TURN
скрывает прямой адрес от собеседника при relay-only, но не от оператора реле.
Оператор сети может классифицировать WebRTC/TURN независимо от шифрования данных.

## Плохая связь

Штатный WebRTC/Opus обеспечивает основу адаптации. Приоритет — аудио, ограничение
исходящего битрейта по измерениям, умеренный буфер и ограниченная передача файлов.
Реальные показатели разборчивости речи и энергопотребления ещё не измерены.
Проверка доступности API кодера не означает доказанное качество в российских сетях.

## Россия и блокировки

Для следующего транспортного этапа нужны независимые точки входа, сменяемые
транспорты и подписанная конфигурация. TURN/TLS сам по себе не является маскировкой
под браузер. Переключение UDP→TCP на том же заблокированном адресе может не помочь.
Прототип не реализует обход DPI и не обещает работу при отключении внешней связи.
