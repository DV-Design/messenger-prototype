# LastCall 0.5 push/wake audit — 2026-10-29

Read-only application audit: Expo 58.0.19, expo-notifications 58.1.6,
React Native 0.88, WebRTC 155, Android APK 0.5.0/code6. Recommendations below
are not implemented fixes or evidence of real push delivery.

## Confirmed cause and current behavior

Main independently verified that production signaling has neither
`GOOGLE_APPLICATION_CREDENTIALS` nor a mounted Firebase Admin credential;
authenticated capabilities still report push=false. Native TURN remains active.
The Firebase Android client is already included in APK 0.5. A separate
`lastcall-push` sender-account form for project `lastcall-f8b4c` is prepared;
action-time credential approval is pending. No issued key or role grant is
claimed by this report.

Code evidence, relative to repository root:

- `apps/mobile/src/components/PushBridge.tsx:24`: push=false prevents requesting
  and registering a device token; the displayed server-not-configured status is
  intentional. Line 33 reconnects on tap/resume, then attempts registration.
- `apps/server/src/providers.ts:19`: the current message combines `notification`
  and `data`; line 21 uses high priority, bounded TTL and the existing channel.
  In Android background this is a system-tray notification, with data handled
  after tapping. It does not itself bootstrap WebRTC.
- `apps/mobile/src/notifications.ts:21`: `shouldPlaySound:false`; Expo documents
  that this also suppresses Android heads-up alerts irrespective of priority.
  Lines 22–27 listen only for tap, token rotation and resume, not notification
  receipt. No background task is defined or registered; TaskManager is absent
  from mobile dependencies.
- `apps/mobile/src/runtime.ts:34`: manager installation replaces the previous
  instance. `boot()` at line 80 is UI-oriented and may create an identity when
  absent. A headless task must not blindly repeat this bootstrap or race UI.
- `apps/mobile/src/storage.ts:10`: existing SecureStore accessibility must not
  be silently weakened to support background operation. Adapter write queues
  are per instance, not proof of cross-runtime exclusion.

Enabling server FCM can make the unchanged 0.5 APK register after reopening,
show a background notification, and synchronize after the user taps it. This
requires notification permission, Play Services, a valid registered token and
the existing recipient watch/consent. It does not add cold background P2P sync.

## Proposed bounded headless path — msg-27d, updated APK required

Use SDK-compatible `expo-task-manager`, define a named task at module scope,
load it before Router, and register through `Notifications.registerTaskAsync`.
Add a receipt listener for a running client and review intentional sound/banner
behavior. Use data-only FCM for headless receipt, retaining TTL, consent, quotas
and content-free intent metadata. Expo Android can visibly present generic
`data.title`/`data.message` on that path; alternatively the task can immediately
post a generic local notification. Validate the chosen path on the actual SDK.

`NotificationTaskPayload` is a `NotificationResponse` or an object containing
`notification`, `data` and optional `aps`. Installed Android
`RemoteMessageSerializer.java` retains raw data fields and sets `dataString`
from `data.body`; current flat FCM data does not supply that JSON string.
Parse bounded raw/JSON payloads defensively, validate kind/ID/deadline, deduplicate
task/receipt/tap callbacks, and never treat push as a content ACK.

Reuse one runtime owner, existing profile/key and encrypted outbox. A cold task
must not register a new user, prompt permissions, open the app UI or microphone.
Bound work by intent expiry and a short execution budget; await persistence and
close only task-owned transports. Foreground takeover must preserve its manager.
Verify TaskManager runtime reuse; if separate contexts can overlap, establish
shared native/storage exclusion before allowing concurrent encrypted-state writes.
The current void `disconnect()` is not an awaited completion boundary.

FCM allows only short processing, not a permanent WebRTC process. Longer work
may need Android WorkManager/foreground-service integration. Keep the seven-day
sender queue for retries; a sleeping/offline/force-stopped recipient cannot be
promised instant delivery. Never auto-start a canceled or expired call.

## Acceptance evidence still required

1. After approved provisioning, preserve TURN configuration and verify push=true.
   Open existing 0.5 on the own `LastCall_Delivery` AVD/user0, retain identity and
   history, grant notifications and confirm token registration without logging it.
2. With sender available, background the recipient with Home, send only after
   direct ACK is absent, and observe an actual system notification. Tap it;
   verify P2P/relay transfer, exact small-file bytes, durable recipient ACK and
   persistence after reopening. Provider acceptance alone is not a pass.
3. For a future headless build, repeat without tapping in background and after
   ordinary process termination. Verify bounded task execution, safe UI takeover,
   no duplicate manager/history loss, malformed/expired intent rejection and no
   late call or microphone capture. Force-stop is a separate expected limitation.
4. Repeat the essential notification/tap/background cases on physical Android
   phones, including locked screen and actual mobile networks. No broad UI matrix.

[Native 0.5 preflight](native-050.md) established Play Services availability,
upgrade/history retention and the configured-client/disabled-server status.
It did **not** establish token issuance, real push receipt or background wake.
On 2026-10-29 main additionally booted the same own AVD with preserved Owner 0
data and observed notification permission currently false for that QA user;
neither that permission nor another Android user's permission was changed.
Main then shut down only that AVD after verifying its name. No actual push
test was performed.
This does not establish the permission state on the user's physical phone.
The read-only audit changed no application, dependency, native or account state.
APNs and system incoming-call integration remain separate.
