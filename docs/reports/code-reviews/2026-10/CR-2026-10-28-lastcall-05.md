# Code review: LastCall 0.5 delivery and network recovery

Date: 2026-10-28. Reviewer: main agent, independent of implementation workers.
Scope: encrypted outbox/attachment storage, durable receipts, signed immutable
group synchronization, native network observer, signaling resume and permissions.
Verdict: PASS for the bounded preview; public carrier/TURN and background push
availability remain open infrastructure work, not a production guarantee.

## Evidence and corrections

Read related history (4b05add/907817b/ddf5e16/f602794), existing protocol/storage,
new implementation and tests. Checked signature purposes and pinned membership,
original deadlines across migration/restart, per-final-recipient receipts, bounded
queues and optional old-frame compatibility. Read all changed mobile persistence,
network observer and attachment UI paths and the new real-browser tests.

Two blocking findings were corrected before accepting:

- `messenger.ts:254`: history trimming could remove an incoming record before its
  save/ACK when a chat already held100 protected outgoing items. Incoming records
  are protected through persistence; a full pending-only history refuses receipt
  instead of acknowledging lost content. Regression included in outbox tests.
- `server.ts:137`: tombstone creation initially read role after clearing it.
  Role/token are captured before cleanup; real close/rejoin in reverse order now
  retains both original roles. Tokens cannot replace another peer without matching.

The complete existing e2e suite then found an explicit-leave regression: all
peer departures had been treated as temporary network loss, leaving the survivor
in error after10s. New optional departure reason is sent only to token-aware
clients. Explicit leave/non-resumable old-client departure immediately returns to
waiting; resumable interruption uses recovery. The original survivor assertion
was preserved and passed. A stale directory test helper was separately changed to
read actual attachment bytes through getFileData; exact-byte assertions remain.

## Durable boundaries and security

- `session.ts:346`: receive queue bounded512frames/12MiB, ordered async callbacks,
  generation/channel guards, no ACK after rejected save or stale disconnect.
- `messenger.ts:257`: text save completes before receipt; duplicate retry attempts
  persistence again. `receiveFile` saves authenticated ciphertext blob and metadata
  before ACK. Outbound `sendFile` commits blob then metadata before transport.
- `group-sync.ts`: distinct Ed25519 purposes for creator roster, original content
  hash/type/author/group/ID/deadline, and final recipient receipts. A relay cannot
  rewrite author, extend TTL or impersonate a missing recipient. No server payload.
- `server.ts:144`: ephemeral resume metadata bounded by maxConnections, expires10s;
  atomic socket replacement prevents an old close removing the new occupant.
- Native network observation uses Expo58-compatible expo-network; Wi-Fi is never
  required. Explicit hangup still releases tracks. Native Firebase client config
  remains separate from the not-yet-issued Admin service key.

## Remaining findings and limits

- P2 `msg-dlz`:16 retained attachment blobs/40MiB includes delivered history. No
  storage-management screen yet. A blob save followed by failed metadata save may
  leave an orphan; crash-safe reconciliation must never delete referenced/pending
  content. Current capacity rejects new sends visibly and preserves waiting items.
- `msg-rw8`: retries restore after restart but re-send whole files, no byte-offset
  checkpoint. Per-file5MiB, text pending100, history500 total/100 per chat, group8.
- P1 `msg-bcw`: no reachable public TURN. STUN alone cannot guarantee connectivity
  across mobile NAT. Physical operator/handover testing remains `msg-9rr`.
- P1 `msg-3z9`: project/client Firebase configured, server service-account creation
  and persistent key await user confirmation. No real FCM/APNs delivery claim.
- Existing protocol audit/ratchet/key lifecycle remains `msg-4vs`. New purpose-bound
  signatures and local encryption do not replace an independent protocol review.
