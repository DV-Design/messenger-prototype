# Review: LastCall 0.4 registration, branding and direct-first wake

Date: 2026-10-28. Scope: changes since 907817b. Main independently reviewed the
identity/profile protocol, SQLite registration/search/pagination, mobile bootstrap,
catalog generations, permission lifecycle, wake state/cancellation, provider TTL,
resource bounds and generated native assets. History of username reassignment and
previous generic wake errors was checked before accepting changes.

## Verdict

PASS as an explicitly labelled technical preview. Production-grade unconditional
instant delivery is not achieved or advertised. No real Firebase/APNs account or
public relay was configured. Profiles persist; content is never put in the server
directory or push body. Existing phone functionality is retired in production.

## Corrected during review

- Server previously allowed an existing key to replace its username. It now
  rejects reassignment, retains canonical displayName on reconnect and enforces
  username immutability in SQLite. The signed purpose-separated resolver recovers
  only the owner's profile and does not register users or replace presence.
- SQLite's default case folding did not handle Russian names. Query and stored
  names now use Unicode NFKC/lowercase folding; literal wildcard inputs stay bound.
- Mobile recovered-profile publication now waits until its client exists; initial
  permission navigation waits for route settlement and does not wait for network
  registration. Manual phone flows and READ/WRITE_CONTACTS were removed.
- The old call-button guard prevented attempts to offline/suspended users despite
  the new bounded wake logic. It now permits an attempt through an online directory.
- Uncorrelated optional-wake provider/expiry/rate errors no longer overwrite chat
  errors. Correlated RPC errors and terminal authorization/transport errors remain.
- Direct transmission precedes wake; ACK within the grace window suppresses it.
  Calls can be cancelled before P2P/media startup, and expired operations cannot
  start late. Files retain at most one bounded sender-memory operation.

## Open findings and limits

- **P1 msg-row** — `packages/core/src/messenger.ts:231` receiveMessage schedules local
  encrypted persistence; `packages/core/src/session.ts:296` can ACK before that write
  is durable. This pre-existing design needs an asynchronous durable ACK boundary
  and crash/write-failure tests before claiming crash-safe delivery.
- **P2 msg-sxc** — `apps/mobile/src/catalog-model.ts:20` load(false) replaces previously
  loaded pages with page one. Focused 30s refresh can reset a >100-user catalog's
  position. Preserve loaded pages/scroll in a follow-up; backend pagination is tested.
- **P2 msg-zvz** — `apps/mobile/src/permissions.ts:17` can receive Android microphone
  state `prompt` after a first denial, and the UI labels that as not yet requested.
  Native grants remain denied and manual retry works. Track the attempted state
  or use neutral not-granted wording; first-launch sequential prompts were verified.
- **msg-218** — recipient watch consent is not a full human contact-request/block
  flow; unknown senders must not get unrestricted wake access through public search.
- **msg-3z9 / msg-bcw** — real Firebase/APNs/system-call integration, physical network
  tests and reachable TURN remain required. Standard WebRTC/TURN can be detected.
- **msg-bkt** — npm audit reports 9 affected toolchain nodes (4 high/5 low), caused
  by Zod3 and deepmerge in Expo build tooling; no critical advisory. Automated
  downgrade to incompatible Expo54/WebRTC-plugin14 was not applied. Server runtime
  audit reports **0 advisories**. No dev server is published.

The installation key provides one server login binding, not an unforgeable
physical-device identifier after uninstall/key loss. Sender-only queues cannot
deliver when the sender is absent. Comparison and references:
[P2P/push study](../../../P2P-WAKE-RESEARCH-RU.md).
