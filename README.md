# LastCall

Android/iOS мессенджер с приоритетом прямого P2P.
Целевая среда — в том числе российские мобильные и домашние сети.
Боты, каналы и резервные копии исключены из объёма.

Версия 0.7.1 меняет установление звонка. Исходящий сначала пытается напрямую; через
2,5 с без ответа отправляется зашифрованное приглашение через сервер/FCM до
передачи медиа. У приглашения стабильный `callId` и исходный 30-секундный срок,
который не продлевается повторами. Получатель расшифровывает его только ключом
закреплённого контакта и проверяет отправителя/получателя, `callId`, срок и членство,
а также текущую эпоху и состояние сервера, прежде чем показать звонок. Явный ответ
лишь запускает ожидание совпадающего P2P-звонка: «принято» не означает «медиа уже
активно». Микрофон и камера включаются только после явного ответа. Собственный
экран звонка не открывает чат или историю и показывается до установления ICE.
Отменённый или истёкший вызов не возобновляется поздним уведомлением.

Сервер хранит только ограниченные метаданные согласования в RAM на время до 30 с
(до 4096 вызовов, до 8 на пользователя) и tombstones отмены; содержимое, медиа и
история звонков не сохраняются. Перезапуск очищает метаданные, смена эпохи делает
старые действия недействительными. Это координация, а не серверный журнал вызовов.

На Android 14+ добавлен отдельный шаг доступа к полноэкранным уведомлениям:
системные настройки открываются по кнопке, а фактическое разрешение перечитывается
после реального выхода из приложения и возврата. Открытие настроек не считается
разрешением. Для обновления используется отдельная отметка, поэтому прежние четыре
запроса доступа повторно не задаются. Без этого доступа ОС может показать только
баннер/уведомление с действиями.

Видео: прежняя петля обратной связи сбрасывала оценку GCC с дисконтом в ручные
ограничения каждые 2 с и периодически выключала поток; это давало паузы кадров
до ~10 с. Теперь действует стабильный потолок 1,8 Мбит/с / 30 кадр/с без уменьшения
разрешения, а фактический битрейт и разрешение выбирает нативный GCC. JS больше не
выключает поток периодически. Исправлены и диагностические поля: только фиксированный
allowlist кодека, кадров/с, размеров, декодированных/пропущенных кадров и зависаний;
недоступное значение показывается как «—». В контролируемом 66-секундном браузерном
RTP-тесте до исправления было 619 кадров, 14 записей параметров и максимальный
разрыв 10,05 с; после — 1321 кадр, 0 периодических записей, максимальный разрыв
2,016 с и 0 заявленных зависаний на каждого участника (выборка ~2 с). Это VP8 и
браузерная проверка, а не доказательство качества на физических Pixel/Vivo или
на всех телефонах.

## Историческая опубликованная версия 0.7.0 / Android code10

Входящий звонок теперь показывает собственный экран LastCall, в том числе поверх
блокировки, и может пробуждать свёрнутый клиент при внешне подключённом RTC-сеансе.
Добавлены подтверждения прочтения: часы → одна галочка после сохранения у адресата
→ две после открытия им чата. Видео начинает с более высокого потолка качества
и адаптируется по реальным потерям/доступной полосе.
Обновите оба телефона поверх прежней версии, без удаления приложения: ключ,
профиль и история сохраняются. Старые строгие схемы не гарантируют обратное
понижение версии после появления новых полей подтверждений.

На собственном Android API36 эмуляторе проверены экран LastCall поверх PIN,
явный ответ с двусторонним RTP после окна пробуждения, истечение входящего и
настоящий FCM-старт после подтверждённого обычного завершения процесса.
Холодное появление входящего заняло 12,95 с; фоновые попытки — около 10,75–10,97 с.
Это измерения одной среды, не обещание мгновенного звонка. Эмулятор был без звука:
RTP подтверждает передачу, но не слышимое качество речи. Физические телефоны,
российские сети, API24–25, отказ в полноэкранном разрешении и качество нативного
видео ещё требуют приёмки. iOS/APNs/CallKit не настроены.
[Точная приёмка 0.7.0](docs/reports/debugging/2026-10/native-070.md).

По новому требованию короткий текстовый preview может проходить через FCM
в зашифрованном виде: до 800 байт UTF-8, с возможным сокращением. Сервер и Firebase
не получают открытый текст или имя файла; для файла передаётся только зашифрованное
краткое имя, без его байтов. FCM может временно держать зашифрованный конверт
до 60 секунд. Видны служебные идентификаторы отправителя/получателя и срок.
Это изменение прежнего режима «push совсем без содержимого». Полная переписка
по-прежнему передаётся P2P, сохраняется у получателя и только затем получает ACK;
preview не добавляет запись в чат и не подтверждает доставку или прочтение.

Нажатие на уведомление открывает существующий чат отправителя, а для
группы — саму группу, как при открытом приложении, так и после холодного запуска.
Получатель проверяет ключ контакта, членство и локальный контекст сервера/профиля;
URL из push не открывается. Отдельно проверяются отсутствие дублей и неверного чата.

Голосовая запись — до 120 секунд в AAC/M4A; видеокружок — до 30 секунд,
целевые 480p на Android / 640×480 на iOS и 600 кбит/с. Для обоих остаётся предел 5 МиБ. Запись начинается
только явным действием в открытом чате: остановить, просмотреть/прослушать,
отправить или отменить. Микрофон в пустой строке чата открывает голосовую запись;
видеокружок доступен через скрепку. После «Отправить» запись сохраняется в очередь,
и отмена этого уже принятого сообщения не обещается. В фоне камера и микрофон
для заметок не записывают.
Голос проигрывается в чате, видео отображается в круге. Сам видеофайл хранит
полный прямоугольный кадр: область за кругом не вырезается и видна при сохранении
или открытии вне LastCall. Не помещайте в неё то, чем не хотите делиться. Передача использует ту же
зашифрованную семидневную очередь файлов и её общую ёмкость 16 файлов / 40 МиБ;
это не отдельное безлимитное хранилище. Параметры кодирования не гарантируют
одинаковый размер или качество на всех устройствах.

На Android 8+ собственный self-managed аккаунт звонков регистрируется автоматически.
Ручное включение аккаунта в приложении «Телефон» и разрешения на телефонные номера,
журнал или обычные телефонные вызовы не нужны. Разрешите уведомления, микрофон и
камеру; на Android 14+ при необходимости откройте «Настройки → Системные звонки →
Открыть настройки звонков» и разрешите полноэкранные уведомления. Без этого ОС
может показать только баннер/уведомление. На API24–25 реализован собственный
резервный экран без self-managed ConnectionService, но он ещё не проверен нативно.
Входящий экран требует действующего аутентифицированного приглашения, а не одного
push. У получателя микрофон/камера не захватываются до явного ответа.
Чат не открывается поверх PIN.

Для обычных данных фон ограничен окном 9 с JS / 12 с нативного владения таймерами;
подготовка typed-звонка получает отдельные до 25 с / 28 с, с ограничением сроком
intent. Живой звонок удерживает отдельного владельца runtime. После исходящего
приглашения через 2,5 с без ответа возможен wake даже при RTC `connected`;
отмена, ответ и срок отменяют устаревшее действие. Это не постоянный фоновый процесс.

Историческая [приёмка 0.6.0](docs/reports/debugging/2026-10/native-060.md) описывает
текст на PIN-lockscreen, переход по уведомлениям текста/файла, прежний managed-
звонок и голосовую запись. Она не заменяет отдельную приёмку нового экрана 0.7.0.

Видеозвонок показывает удалённое видео на весь экран и своё в небольшом окне.
Захват запрашивается до 720p/30 кадров/с; начальный потолок — 1,8 Мбит/с без
уменьшения разрешения. Это пределы, а не гарантированное качество: штатный WebRTC
congestion control выбирает реальный поток. Отсутствие оценки полосы и высокая
задержка маршрута сами по себе больше не удерживают прежние 300 кбит/с.
В опубликованной 0.7.0 JS дополнительно пересчитывал ограничения по оценке GCC
каждые 2 с; это оказалось источником длинных пауз кадров на части маршрутов и
исправлено в опубликованной 0.7.1. Историческое описание 0.7.0 не означает, что
ступенчатое управление сохраняется в новом кандидате.
На крайне узком канале видео может временно приостанавливаться.
Системный входящий экран появляется при блокировке; полноэкранное видео в LastCall
требует открытого приложения/разблокировки. PIN не обходится.

## Очередь и соединения

Текст и файлы ожидают подтверждения получателя в зашифрованном хранилище
отправителя до семи дней от исходной отправки. Перезапуск и повторная передача
не продлевают срок. Файл сохраняется до сетевой отправки; подтверждение приходит
после записи на устройстве получателя. При разрыве файл передаётся целиком с тем
же ID; продолжения с последнего байта пока нет. Истёкшая отправка помечается явно.
Лимиты preview: 100 ожидающих текстов, 16 сохранённых файлов / 40 МиБ суммарно,
до 5 МиБ на файл. Подтверждённые файлы тоже занимают эту ёмкость; интерфейс
управления сохранёнными файлами ещё не добавлен. Переполнение не удаляет очередь.

В группах до восьми участников телефоны синхронизируют сохранённые записи и файлы.
Другой участник может дослать их, пока автор офлайн. Подписаны состав группы,
исходное авторство, содержимое/хеш файла, срок и подтверждения отдельных получателей.
Копии не продлевают семидневный срок синхронизации. Все участники этой проверки
должны обновиться до опубликованной 0.7.2/code12. [Контракт очереди](docs/OUTBOX-CONTRACT.md).

Часы означают ожидание подтверждения полного сохранения сообщения или вложения;
одна галочка — такую доставку, две — фактическое открытие чата в активном приложении.
Push-preview, другой чат и свёрнутый экран не дают прочтения. Для вложений прочтение
означает показ полученного вложения в чате, а не полный просмотр/прослушивание.
В группе видны счётчики доставленных/прочитавших; галочки требуют всех исходных
адресатов. Подписанные Ed25519 read receipts и `readBy` хранятся зашифрованно на
телефонах и повторяются исходному автору после восстановления связи, включая
перезапуск и отсутствие автора в момент чтения. Серверной очереди подтверждений нет.

Смена доступной сети и возврат приложения вызывают восстановление служебного
подключения и ICE restart. Активный WebRTC-сеанс и медиа сохраняются при попытке
восстановления в течение 10 секунд. Это не гарантия непрерывного звука без сети.
При недоступном прямом маршруте доступен аутентифицированный TURN-резерв
через UDP/TCP/TLS. Реальные российские операторы ещё требуют испытаний.
[Контракт восстановления](docs/NETWORK-HANDOVER-CONTRACT.md).

Регистрация без номера: один уникальный username закрепляется за защищённым
ключом установки. Сервер подтверждает регистрацию и хранит профиль; при повторном
входе возвращается сохранённый профиль, а зарегистрировать другой username тем же
ключом нельзя. Имя для отображения может повторяться. Обновление сохраняет ключ
и историю; потеря ключа после удаления/сброса приложения не даёт восстановления
по одному публичному логину и не равна аппаратной идентификации устройства.

Во вкладке «Контакты» загружается серверный каталог с обновлением и страницами
по 100 профилей. Поиск работает по логину и имени, включая регистр русских букв.
Офлайн-профили остаются доступны в каталоге. SMS и доступ к телефонной книге не
нужны; активные экраны привязки номера удалены. Контракт:
[регистрация](docs/USERNAME-CONTRACT.md).

Firebase FCM на сервере подключён; аутентифицированный клиент видит push=true
и relay=true. Выделенная серверная учётная запись имеет только роль отправки FCM;
её закрытый ключ не входит в репозиторий, APK или публичную загрузку. Android
клиентская конфигурация включена в приложение. В текущей версии поддерживаются
data-only wake, локально расшифровываемые preview и собственные Android-звонки.
Успех FCM не подтверждает сохранение содержимого или прочтение. iOS/APNs не подключён.
[Настройка уведомлений](infra/public/SERVICES.md).

Получатель включает data-only push только после успешной регистрации фоновой
задачи; отдельная готовность native preview разрешает зашифрованный текст/имя файла.
Фоновая работа сохраняет существующий профиль и локальную очередь; legacy-токены
сохраняют уведомление с открытием по нажатию. Исторические результаты без нажатия
для текста/малого файла приведены выше, новая приёмка звонков — в отчёте 0.7.1.
Ни один результат не относится к Android force-stop или каждому физическому телефону.

Логотип обновлён по пользовательскому образцу. При первом запуске системные
разрешения микрофона, камеры, фото и уведомлений запрашиваются последовательно,
до регистрации; отказ от одного не блокирует остальные. Разрешение уведомлений
не заменяет настройку Firebase.

Передача сначала пробует P2P. Если за 2,5 секунды нет ACK, формируется короткий
wake-intent: сообщение/файл/звонок; для текста/имени файла новый клиент может
получить зашифрованный preview. После call-invite действует также отдельная
проверка отсутствия ответа при уже соединённом RTC-сеансе. Ожидание соединения для звонка
ограничено 30 секундами и отменяется кнопкой завершения. Текст и файлы ожидают
получателя в локальной семидневной очереди. Отдельная попытка передачи файла
имеет таймаут, после которого очередь повторяет её. FCM не получает открытый текст
переписки, имена файлов, SDP или ключи. Начиная с 0.6.0 допускается только
ограниченный зашифрованный preview со служебными заголовками. Служебный сервер
хранит профили, имена и публичные ключи устройств, push-токены, согласия и лимиты;
signaling пересылает непрозрачные зашифрованные данные установления связи.
Секретный ключ устройства остаётся на нём. TURN пересылает зашифрованные пакеты
и расходует серверную полосу, без архива переписки.
[Исследование и варианты](docs/P2P-WAKE-RESEARCH-RU.md),
[контракт wake](docs/WAKE-CONTRACT.md). Мгновенная доставка недоступному устройству
без дополнительного хранилища невозможна.

## Что реализовано

- Общий клиент Android/iOS на React Native с native WebRTC.
- Постоянный профиль устройства, поиск по @username, контакты и статусы.
- Общее служебное подключение к каталогу, независимые P2P-сеансы с собеседниками.
- Знакомый список чатов/контактов, экран переписки, глобальное окно звонка.
- Группы до 8 участников: текст и файлы прямой рассылкой каждому участнику.
- Подписанная авторизация Ed25519; приглашение пары выводится через X25519/HKDF.
- Зашифрованные локальные контакты, группы, текстовая история и очередь отправителя.
- Аутентифицированное шифрование служебного обмена, без передачи секрета серверу.
- Текст и файлы до 5 МиБ по WebRTC DataChannel.
- Аудио/видеозвонки 1:1: принять, отклонить, отключить микрофон, завершить.
- Прямой ICE-маршрут и режим «только через TURN» без скрытого перехода на прямой.
- Диагностика реального маршрута, RTT, аудиобитрейта, jitter и потерь.
- Ограничение аудиобитрейта по доступным RTT/remote loss показателям WebRTC.
- Сервер с ограничениями ресурсов и выдачей временных TURN REST credentials
  после авторизации устройства; публичный TURN включён с TTL credentials 600 секунд.
- Браузерный испытательный клиент с тем же ядром, автоматические WebRTC проверки.

Это тестовый этап. Для личной прямой передачи оба клиента должны быть доступны.
Ожидающий текст хранится у отправителя и доставляется, когда оба снова в сети;
серверной офлайн-почты нет. Настроенный FCM передаёт wake и ограниченные
зашифрованные preview; успех отправки push не считается доставкой сообщения.
Голосовые и видеокружки используют тот же файловый путь, звонки — собственный
экран LastCall. Групповые звонки и мультиустройства пока недоступны. Переход между экранами не разрывает соединения;
обычный фон не закрывается намеренно, но ОС может приостановить процесс.
Реализация не проходила независимый аудит и не реализует ratchet.
Не заявляется устойчивость к DPI: стандартный WebRTC/TURN может определяться и
блокироваться. Прямой P2P раскрывает IP собеседнику.

## Быстрый локальный запуск

Нужен **Node.js 24 LTS**; версия записана в `.node-version`. Системный Node 25
не поддерживается выбранными Expo/React Native. Из корня репозитория:

```sh
npm ci
npm run dev:server
```

Во втором терминале:

```sh
npm run dev:probe
```

Откройте `http://127.0.0.1:5173` в двух независимых окнах/профилях браузера.
Сервер: `http://127.0.0.1:8787`. Создайте приглашение в одном клиенте и передайте
его второму по доверенному каналу. Нажмите «Подключиться» на обоих клиентах.
Дальше можно передать текст, файл или предложить звонок. Камера и микрофон
запрашиваются только для звонка. Секретное приглашение нельзя публиковать.

Без настроенного STUN/TURN прямой маршрут проверяется только там, где устройства
могут найти друг друга самостоятельно, например на одной машине/в одной LAN.
Выход в разные сети требует своей ICE-инфраструктуры. Публичных STUN/TURN по
умолчанию нет. Сервер слушает loopback; в LAN его выводят явным `HOST=0.0.0.0`.
Для внешней сети нужны HTTPS/WSS и контроль доступа к TURN provisioning.

## Android и iOS

См. [инструкцию мобильного клиента](apps/mobile/README.md).
Expo Go не поддерживает этот native WebRTC: требуется development build.
Для Android нужны JDK 21 и Android SDK, для локальной сборки iOS — полный Xcode.
JavaScript export обеих платформ проверяется отдельно от нативной сборки.

```sh
MESSENGER_ALLOW_LOCAL_HTTP=1 npm run native:prebuild -w @messenger/mobile
npm run android -w @messenger/mobile
```

Физический телефон обращается к LAN-адресу компьютера, а не к `localhost`.
Для Android emulator сервер компьютера обычно доступен как `10.0.2.2`.
Локальный HTTP разрешается только в явно подготовленной dev-сборке.
Секреты и `.env` не должны попадать в Git. Имя пакета `dev.messenger.prototype`
временное и не является выбранным названием продукта.

медиа-проверка проверяет реальный приём потока и закрытие локальных источников.

с ACK в обе стороны, точные байты файла и входящий аудио-RTP в обе стороны.

Проверка TURN относится к серверной инфраструктуре. Новая фоновая логика требует
обновления обоих Android-приложений до текущего выпуска.

не выбрана.
